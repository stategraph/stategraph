title: when_modified

The `when_modified` configuration allows you to configure autoplan and autoapply operations based on pull request file changes. This enables you to automatically trigger plan and apply operations when specific files are modified in your repository.

## Configuration Levels

The `when_modified` configuration can be set at three different levels, all using the same syntax:

1. **Global level** - Applied to all directories unless overridden
2. **Directory level** - Set under `dirs.<directory>.when_modified` to override global settings for a specific directory
3. **Workspace level** - Set under `dirs.<directory>.workspaces.<workspace>.when_modified` to override settings for a specific workspace

All three levels support the exact same configuration options. More specific configurations override broader ones (workspace > directory > global).

## Default Configuration
```yaml
when_modified:
  file_patterns: ["${DIR}/*.tf", "${DIR}/*.tfvars"]
  autoplan: true
  autoplan_draft_pr: true
  autoapply: false
  depends_on: ""
```

## Keys
| Key                  | Type    | Description                                                                                       |
|----------------------|---------|---------------------------------------------------------------------------------------------------|
| file_patterns        | List    | List of file globs to identify changes in a directory. Always relative to the root of the repository. Prefix with `!` to exclude a file glob. Default is `["${DIR}/*.tf", "${DIR}/*.tfvars"]`. The configuration schema spells the default `["**/*.tf", "**/*.tfvars"]`; a leading `**/` is treated as `${DIR}/`, so the two forms are equivalent. |
| autoplan             | Boolean | Automatically run a plan operation on a new pull request or an update on an existing one. Default is true. |
| autoplan_draft_pr    | Boolean | Automatically run a plan operation on a new draft pull request or an update on an existing one. Default is true. |
| autoapply            | Boolean | Automatically run an apply operation after merging a pull request. Default is false. |
| depends_on           | String or Object | Defines dependencies between different directories or environments, allowing for sequential operations. Supports `dir:` for absolute paths or `relative_dir:` for relative paths within the repository. Can also combine dependencies using [tag queries](/advanced-workflows/tags/#tag-query-syntax). Default is an empty string. May also be an object to enable additional behavior such as `prune_on_no_change` (see [Depends-On](#depends-on)). |
| prechecks            | List    | Cheap checks that decide, before any setup job runs, whether a pull request is worth any work. Only valid in the global `when_modified`. Default is an empty list. See [Prechecks](#prechecks). |

### File Patterns
The `file_patterns` key specifies a list of file globs that identify changes in a directory. These patterns are relative to the root of the repository.

### Prechecks

Autoplan normally has to run the [tree builder](/reference/configuration/tree-builder), the [config builder](/reference/configuration/config-builder) and the [indexer](/reference/configuration/indexer) before Terrateam can tell whether a pull request changes anything it manages. Each of those costs a CI run on every pull request, including the ones that turn out to need no work at all.

`prechecks` lets you give Terrateam a hint so it can answer sooner. Every check is evaluated against the static configuration in your repository and the pull request itself. If **any** check is false, Terrateam does nothing and no CI run is started.

```yaml
when_modified:
  prechecks:
    - user: ['!renovate[bot]']
    - file_patterns: ['!docs/**']
    - config_file_patterns:
        stale_config_min: 60
```

`prechecks` is only valid in the **global** `when_modified`. Setting it under `dirs.<directory>.when_modified` is a configuration error: a precheck is a decision about the whole pull request, taken before any directory is known.

Prechecks are read only from the configuration committed to your repository. A `prechecks` list that the config builder produces is ignored, because a precheck exists to decide whether the config builder should run at all.

#### Checks

| Check | Description |
|-------|-------------|
| `user` | A list of user names. The check passes when the user who **opened** the pull request matches the list. The pusher is not considered. |
| `file_patterns` | A list of file globs. The check passes when any file the pull request changes matches the list. These globs are repository paths and take no `${DIR}` prefix. |
| `config_file_patterns` | The check passes when a file the pull request changes matches a directory in the configuration Terrateam derived for the destination branch. Takes `stale_config_min`, how many minutes may pass since that configuration was last derived. |

#### Negation and the implicit `'*'`

Both `user` and `file_patterns` accept entries prefixed with `!`, which exclude rather than include. The rule for a list is:

- a list of **only** negations carries an implicit `'*'`, so it matches everything the negations do not exclude;
- a **mixed** list carries no implicit `'*'`, so at least one positive entry must also match;
- an **empty** list matches nothing.

So `['!docs/**']` means "any change outside `docs/`", while `['infra/**', '!docs/**']` means "a change under `infra/` that is not under `docs/`".

#### When a check cannot answer

A check that cannot read the data it needs passes, so that the usual evaluation continues. `config_file_patterns` passes when no configuration has been derived for the destination branch yet, when the one it finds is older than `stale_config_min`, or when the pull request changes the Terrateam configuration file itself. A `stale_config_min` of `0` makes every configuration stale, which disables the check.

`file_patterns` and `config_file_patterns` also pass when the pull request is large enough that the VCS truncates the file list it reports. GitHub stops at 3000 files and does not say that it stopped, so a longer list may be missing the very file a check looks for. Terrateam treats such a list as no answer rather than as an answer of "nothing matched", so a very large pull request is always evaluated normally.

The age is measured from the last time Terrateam derived that configuration, not from the first. A pull request that falls through because the configuration went stale derives it again on the way past, so the next pull request against that branch finds a fresh one. The check therefore recovers by itself on a branch nobody pushes to; it costs the first pull request after the window a full evaluation.

A derived configuration is recorded by a push to the default branch, and by the evaluation of any pull request against a branch. So `config_file_patterns` cannot answer for a destination branch that nothing has evaluated yet, and that pull request is evaluated normally.

#### Which configuration the check reads

Terrateam reads the recent commits of the destination branch and keeps only the configurations that were derived at one of those commits. Of those, it takes the one derived at the commit nearest to the branch head.

This matters because a repository holds a derived configuration for every branch Terrateam has evaluated, and the most recently derived one can belong to a branch that rearranged the directories completely. A configuration produced at a commit of the destination branch is a real earlier state of that branch, so it is the safe one to reuse. It also means a force push or a rebase of the destination branch cannot leave the check reading a configuration for a commit that no longer exists there.

Only recent commits are read, so a configuration derived far back in the history is not found. That costs nothing in practice, because `stale_config_min` would reject it anyway.

#### Prechecks read the VCS diff

The checks that read the changed files — `file_patterns` and `config_file_patterns` — use the file list the VCS reports for the pull request. That is deliberate, and it is what makes them prechecks: they answer before Terrateam does any work, using only what is already at hand.

If you enable the [tree builder](/reference/configuration/tree-builder), the rest of the evaluation works from a different list. The tree builder decides for itself which files a pull request changes, and it can mark a file that the VCS diff does not list at all — a directory whose module dependency moved, for instance. Getting that list means running the tree builder, which is the CI run the precheck exists to skip, so a precheck cannot wait for it.

The consequence is worth knowing when you write the checks: a precheck decides on the VCS diff alone, so a pull request whose only relevant change is one the tree builder would have found is stopped. That is the trade the hint buys you. Write your patterns against the paths the VCS reports.

#### Overriding a precheck

Prechecks apply only to autoplan. Commenting `terrateam plan` runs the pull request regardless, and from that point the prechecks no longer apply to a later commit on it. The later layers of a layered run never consult prechecks at all.

#### Prechecks and the apply check

A pull request that a precheck stopped still has to be mergeable. If [`apply_requirements.create_completed_apply_check_on_noop`](/reference/configuration/apply-requirements) is `true`, the completed `terrateam apply` check is created even though no work was done.

### Auto-Plan
The `autoplan` key enables or disables automatic plan operations on new pull requests or updates to existing ones.

### Auto-Plan Draft Pull Request
The `autoplan_draft_pr` key enables or disables automatic plan operations on new draft pull requests or updates to existing ones.

### Auto-Apply
The `autoapply` key enables or disables automatic apply operations after merging a pull request.

### Depends-On
The `depends_on` key allows you to specify dependencies on other directories within your repository. This is particularly useful in scenarios where your infrastructure is structured into functional layers that must be deployed in a specific order. For example, a network setup must be applied before a managed PostgreSQL service can be deployed, as the latter might depend on outputs from the former.

#### Key Features
- Layered Operations: Supports multi-layered operations, where each layer depends on the successful apply of the previous one.
- Dependency Management: Automatically triggers plan and apply operations based on changes in the lowest layer, and cascades through dependent layers.

While the `depends_on` key can be specified in the top-level `when_modified` configuration (which would make ALL directories depend on the specified directories), it is strongly recommended to define dependencies at the directory or workspace level for better control. Use `dirs.<directory>.when_modified.depends_on` or `dirs.<directory>.workspaces.<workspace>.when_modified.depends_on` instead.

A top-level `depends_on` is also incompatible with the [`stacks`](/reference/configuration/stacks/) section: it applies to every directory, so it names directories outside the stack of the directory that carries it, which is an error. See [`depends_on` and Stacks](#depends_on-and-stacks) below.

#### `depends_on` and Stacks
A `depends_on` gives the order inside one stack. It cannot reach out of the stack it is written in.

If you use the [`stacks`](/reference/configuration/stacks/) section, every directory a `depends_on` names must be in the same stack as the directory that declares it, or in a stack that shares a nested stack with it. A `depends_on` that reaches into an unrelated stack is a configuration error, and the run reports it instead of planning.

Two directories are in the same stack when the paths to their stacks have a stack in common. That is the stack itself when they are in the same stack, and a nested stack that holds both when they are in two different ones. To order two stacks that share nothing, use the `plan_after` or `apply_after` rule of the `stacks` section, which is what those rules are for.

A repository with no `stacks` section is unaffected: every directory is in the same stack there.

#### Object Form and `prune_on_no_change`
The `depends_on` value may be either a string (a tag query) or an object. The object form lets you set additional options alongside the dependency:

| Key                 | Type    | Description                                                                                       |
|---------------------|---------|---------------------------------------------------------------------------------------------------|
| tag_query           | String  | The dependency tag query, equivalent to the string form of `depends_on`. Required. |
| prune_on_no_change  | Boolean | When `true`, the dirspace still participates in layering calculations, but if it has no changes of its own it is dropped from evaluation even when something it depends on changes. Default is `false`. |

By default, when a dependency of a dirspace changes, that dirspace is pulled into the run even if it has no changes itself. Setting `prune_on_no_change: true` keeps the dirspace in the dependency ordering for any layers that depend on it, but excludes it from the run unless it has its own changes.

```yaml
dirs:
  database:
    when_modified:
      depends_on:
        tag_query: 'dir:network'
        prune_on_no_change: true
      file_patterns: ["${DIR}/*.tf"]
```
In this example, `database` is ordered after `network` in layering calculations, but it is only planned and applied when `database` itself has changes — a change in `network` alone will not trigger it.

## Configuration Examples

### Same Configuration at Different Levels

The following three configurations achieve the same result for the `production` directory:

#### 1. Global Level Configuration
```yaml
when_modified:
  file_patterns: ["${DIR}/*.tf", "${DIR}/*.tfvars"]
  autoplan: true
  autoapply: false
```

#### 2. Directory Level Configuration
```yaml
dirs:
  production:
    when_modified:
      file_patterns: ["${DIR}/*.tf", "${DIR}/*.tfvars"]
      autoplan: true
      autoapply: false
```

#### 3. Workspace Level Configuration
```yaml
dirs:
  production:
    workspaces:
      default:
        when_modified:
          file_patterns: ["${DIR}/*.tf", "${DIR}/*.tfvars"]
          autoplan: true
          autoapply: false
```

### Auto-Plan on Terraform File Changes
```yaml
when_modified:
  file_patterns: ["${DIR}/*.tf"]
  autoplan: true
  autoplan_draft_pr: false
  autoapply: false
```
This configuration triggers a plan operation automatically when any `.tf` file in the repository is modified. It does not trigger plans on draft pull requests and does not automatically apply changes after merging.

### Auto-Plan and Auto-Apply on Terraform and tfvars File Changes
```yaml
when_modified:
  file_patterns: ["${DIR}/*.tf", "${DIR}/*.tfvars"]
  autoplan: true
  autoplan_draft_pr: true
  autoapply: true
```
This configuration triggers plan operations automatically on changes to `.tf` or `.tfvars` files, including draft pull requests. It also automatically applies changes after merging and creates a status check for pending applies.

### Exclude Certain Files from Triggering Auto-Plan
```yaml
when_modified:
  file_patterns: ["${DIR}/*.tf", "!**/modules/**/*.tf"]
  autoplan: true
  autoplan_draft_pr: true
  autoapply: false
```
This configuration triggers plan operations automatically on changes to `.tf` files, including draft pull requests, but excludes `.tf` files in the `modules` directory and its subdirectories.

### Auto-Plan with Single Dependency
```yaml
dirs:
  "database/":
    when_modified:
      depends_on: "relative_dir:../base"
```
This configuration triggers a plan operation for the `database` directory if changes are found in the `base` directory.

### Depends-On with Multiple Dependencies
```yaml
dirs:
  network:
    when_modified:
      file_patterns: ["${DIR}/*.tf"]
  database:
    when_modified:
      depends_on: 'dir:network'
      file_patterns: ["${DIR}/*.tf"]
  application:
    when_modified:
      depends_on: 'dir:database'
      file_patterns: ["${DIR}/*.tf"]
```
This configuration triggers a plan operation for the `network` layer if changes are detected. If the apply for the `network` layer is successful, a plan operation will be triggered for the `database` layer, which depends on `network`. If the `database` layer's apply is successful, the process continues with a plan operation for the `application` layer, and so on.

:::note
- A lock is acquired regardless of the success or failure of an apply.
- Once a single dirspace has been applied in a pull request, that pull request owns locks on all targeted dirspaces associated with the pull request.
- A lock is only released after a successful apply and merge.
- A lock can be forcefully unlocked by commenting `terrateam unlock` on the pull request.
:::
